# Lightning + StriveX

> Актуальная интеграция версии 2.2.0 использует новый Gateway `ADAPTER=gameserver` и локальный WebSocket `ws://127.0.0.1:4200`. Пошаговый запуск описан в `STRIVEX_SERVER_START.md`. Разделы ниже про отдельный COM-порт StriveX сохранены только как документация устаревшего совместимого транспорта.

## Карта существующей игры

- Полная игровая попытка начинается в `public/app.js`, функция `startGame()`. Внутренние раунды начинаются через `GameEngine.makeRound()`, `beginMatchRound()`, `beginSequenceRound()` и функции `start...` в `AdvancedGameEngine`.
- Внутренний классический раунд заканчивается, когда `GameEngine.press()` возвращает `roundComplete`. Раунд «Захвата цвета» заканчивается в `finishPaintRound()`. Полная попытка заканчивается в `finish(cause)`.
- Числовой результат игры — массив `state.scores` для синего и оранжевого игроков. Для обязательного скалярного результата StriveX используется лучший итоговый счёт: `Math.max(...state.scores)`. Оба счёта, победитель, режим, сложность и число раундов передаются в JSON meta.
- Ошибочный ответ внутри цветовых режимов не завершает попытку, а запускает следующий внутренний раунд. Истечение общего игрового таймера — `TIMEOUT`; ручная отмена — `FAILED` с `fail_reason=cancelled`; новый `START` во время попытки завершает прежнюю как `FAILED` с `fail_reason=superseded`; отключение одной из USB-плат или LED-контроллера во время попытки — `ERROR`. Ранее в проекте не было отдельного состояния проигрыша всей попытки.
- Основной цикл находится в `requestAnimationFrame(tick)` внутри `startGame()`. USB-кнопки опрашиваются отдельным неблокирующим `requestAnimationFrame(poll)`.
- Для последовательного порта уже использовались `serialport` и `@serialport/parser-readline`. StriveX использует существующую зависимость `serialport`, но отдельный порт и собственный построчный протокол. Arduino продолжает работать через `lib/serial-bridge.js`.

## Архитектура

`lib/strivex-protocol.js` не зависит от Electron и COM-порта. Он собирает частичные строки, разделяет несколько команд из одного буфера, понимает `\n`/`\r\n`, отбрасывает пустые строки и защищает жизненный цикл от повторных запусков и двойных финалов.

`lib/strivex-serial.js` открывает только явно заданный COM-порт StriveX, читает его асинхронно и переподключается после обрыва. После каждого успешного подключения протокол отправляет `READY`. Финальные сообщения при отсутствии соединения отмечаются в журнале как недоставленные и намеренно не ставятся в локальную очередь.

`main.js` связывает транспорт, протокол и Electron IPC. `public/app.js` получает только высокоуровневые события `start`/`deny` и отправляет единственный финальный исход.

Состояния интеграции: `disconnected`, `idle`, `running`, `finishing`, `error`. После финального сообщения состояние возвращается в `idle` (либо `disconnected`, если порт закрыт).

## Настройка

В `config.json`:

```json
"strivex": {
  "enabled": true,
  "port": "COM10",
  "baudRate": 115200,
  "reconnectMs": 3000,
  "developmentMode": false,
  "defaultMode": "classic",
  "defaultDifficulty": "easy",
  "defaultVariant": "score",
  "durationMinutes": 1
}
```

COM-порт Arduino задаётся отдельно в блоке `serial`. Один физический COM-порт нельзя назначать одновременно Arduino и StriveX Gateway.

Переменные окружения имеют приоритет:

```bat
set STRIVEX_ENABLED=true
set STRIVEX_SERIAL_PORT=COM10
set STRIVEX_SERIAL_BAUD=115200
set STRIVEX_RECONNECT_MS=3000
npm start
```

## Установка, тесты и запуск

```bat
cd /d "C:\path\to\lightning_windows_v2.1.0_strivex"
npm install --include=dev
npm run check
npm start
```

```bat
scripts\build-exe.bat
```

## Режим разработки

При `developmentMode: true` на сенсорном экране отображается панель состояния, текущий `session_id`, последние исходящие строки и кнопки `Simulate START`, `RESULT`, `FAILED`, `TIMEOUT`. При выключенном реальном StriveX панель использует локальную эмуляцию транспорта.

## Проверка со StriveX Gateway

1. Указать разные COM-порты для Arduino и StriveX, включить `strivex.enabled`, выключить `developmentMode`.
2. Запустить `npm run check`, затем игру и Gateway.
3. Убедиться, что после открытия порта Gateway получил ровно одну строку `READY`.
4. Отправить `DENY:expired\r\n`: игра не должна стартовать, на экране появляется причина отказа.
5. Отправить `START:<новый_uuid>\n`: должен начаться один обратный отсчёт и одна попытка.
6. Повторить тот же `START` и отправить его частями: второй раунд не должен запуститься.
7. Для обычного режима дождаться истечения общего таймера: Gateway должен получить ровно один `TIMEOUT`.
8. Начать новую сессию и нажать «Закончить игру»: Gateway должен получить один `FAILED` с компактным JSON.
9. Во время новой сессии отключить одну USB-плату: Gateway должен получить один `ERROR:USB controller disconnected`.
10. Для проверки `RESULT` использовать режим разработки или штатно завершить режим из фиксированного числа раундов. Убедиться, что число конечное, JSON расположен в той же строке и повторного финала нет.
11. Разорвать StriveX COM-соединение: игра не должна закрыться. После восстановления Gateway должен снова получить `READY`; старый финал автоматически не повторяется.

Автоматические тесты проверяют парсинг частичных/совмещённых строк, защиту от повторного `START`, `DENY`, единственность `RESULT`/`FAILED`/`TIMEOUT`/`ERROR`, компактный JSON и готовность к следующей сессии. Фактический обмен с физическим StriveX Gateway этими тестами не подтверждается и должен быть выполнен по сценарию выше.
